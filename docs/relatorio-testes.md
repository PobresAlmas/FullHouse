# Relatório geral dos testes — FullHouse

**Atualizado em:** 15/11/2026

**Escopo:** inventário dos testes existentes em `backend/` e `web/`, seus objetivos, rotas relacionadas e situação da última execução.

## Resumo

| Conjunto                        |                             Inventário | Última situação verificada                                       |
| ------------------------------- | -------------------------------------: | ---------------------------------------------------------------- |
| Backend unitário                |                42 arquivos `*.spec.ts` | **308 testes aprovados**                                         |
| Frontend unitário/UI            | 56 arquivos `*.test.ts` e `*.test.tsx` | **175 testes aprovados** com Node 22                             |
| Backend HTTP/e2e                |            11 arquivos `*.e2e-spec.ts` | **58 testes aprovados**                                          |
| Backend integração de migrações |     2 arquivos `*.integration.test.ts` | **5 testes ignorados**: `TEST_DATABASE_URL` não está configurada |

Os números acima vêm de execuções feitas nesta revisão em Node 22. Os 308 testes unitários do backend, os 175 testes unitários/UI do frontend e os 58 testes HTTP/e2e do backend passaram. A cobertura inclui explicitamente os arquivos de produção; as suítes que dependem de PostgreSQL foram ignoradas sem `TEST_DATABASE_URL`.

## Como executar

| Diretório  | Comando                                     | O que executa                                                               |
| ---------- | ------------------------------------------- | --------------------------------------------------------------------------- |
| `backend/` | `pnpm test`                                 | Testes unitários Vitest em arquivos `*.spec.ts`                             |
| `backend/` | `pnpm test:e2e`                             | Testes HTTP/e2e em arquivos `*.e2e-spec.ts`                                 |
| `backend/` | `pnpm test:integration:sprint02-migrations` | Integrações de migração em `test/integration/`                              |
| `web/`     | `pnpm test --run`                           | Testes Vitest de componentes, páginas e serviços, sem modo watch            |
| `web/`     | `pnpm test:coverage`                        | Suíte do frontend com relatório e limites de cobertura configurados em 100% |

As configurações estão em [backend/vitest.config.ts](../backend/vitest.config.ts), [backend/vitest.config.e2e.ts](../backend/vitest.config.e2e.ts), [backend/vitest.config.integration.ts](../backend/vitest.config.integration.ts) e [web/vitest.config.mts](../web/vitest.config.mts).

## Resultado da última execução

### Backend unitário

Comando: `pnpm test:cov`, dentro de `backend/` (executa a suíte unitária e mede cobertura).

- 42 arquivos passaram.
- 308 testes passaram.
- Duração registrada: aproximadamente 16 segundos com cobertura.
- Execução feita em Node 22 via `npm exec --yes --package=node@22 -- pnpm test:cov`.
- A suíte unitária não exige banco de dados: os testes isolam serviços, repositórios e integrações por mocks.

### Frontend unitário e de interface

Comando: `npm exec --yes --package=node@22 -- pnpm test --run`, dentro de `web/` (Node 22.23.3).

- 56 arquivos passaram, com 175 testes aprovados.
- A execução usou Node 22 temporariamente via `npm exec`; não alterou a versão de Node do sistema.
- A configuração do Vitest foi renomeada para `.mts` e passou a usar resolução de aliases embutida no Vite; a suíte passou sem os avisos de configuração anteriores.

### Medição de cobertura

Cobertura do backend medida com `pnpm test:cov`, usando o provider V8 e inclusão explícita dos arquivos `backend/src/**/*.ts` (exceto arquivos gerados, declarações e testes):

| Métrica    | Cobertura |
| ---------- | --------: |
| Statements |    62,41% |
| Branches   |    45,50% |
| Functions  |    55,85% |
| Lines      |    63,16% |

- O backend usa Vitest, não Jest. Sua configuração declara `coverage.include` para todo `src/**/*.ts`, evitando que módulos não importados pelos testes desapareçam do relatório. O comando correspondente é `pnpm test:cov` dentro de `backend/`.
- Cobertura frontend em `pnpm test:coverage`: statements 46,68%, branches 40,91%, functions 40,31% e lines 47,98%. O comando executa os 175 testes, mas termina com código 1 porque a configuração exige 100% em todas as métricas.
- Os limites de 100% do frontend não representam cobertura alcançada; hoje eles fazem o comando de cobertura falhar. A lacuna é especialmente ampla em páginas e componentes de tarefas, formulários de despesas, clientes de API de tarefas/pets/residências e utilitários da despensa.

### E2E e integração

O comando `pnpm test:e2e` passou em 11 arquivos e 58 testes em Node 22. Os testes montam controllers Nest em um servidor HTTP de teste e substituem serviços por mocks; validam rotas, guards, DTOs e ligação controller-serviço, mas não persistência real. O build de produção também passou com `npm exec --yes --package=node@22 -- pnpm build`. A execução de integração foi feita: os dois arquivos e cinco casos foram ignorados porque `TEST_DATABASE_URL` não está configurada. As integrações aplicam migrações reais em PostgreSQL. Gere o cliente Prisma com `pnpm db:generate` antes das suítes que importam enums do schema.

O ESLint e o Prettier também passaram nos arquivos alterados.

## Cobertura de rotas: observações

- As rotas de autenticação têm testes unitários do controller/serviço no backend, testes do cliente HTTP/interface no frontend e um teste e2e do limite em `POST /auth/login`. Cadastro, logout e recuperação de senha ainda não têm teste HTTP e2e.
- O controller de autenticação limita requisições a 20 por minuto e a aplicação aplica limite global de 120 por minuto ([auth.controller.ts](../backend/src/auth/auth.controller.ts), [app.module.ts](../backend/src/app.module.ts)). A aplicação não implementa bloqueio de conta após tentativas inválidas. O teste e2e exercita a configuração de throttling em um módulo Nest de teste que repete o guard global e o limite configurados; não inicializa o `AppModule` de produção.
- O e2e de tarefas cobre tarefas de residência (`/residences/:residenceId/tasks`) e as rotas de troca (`/residences/:residenceId/task-exchange-requests`); as rotas de tarefas pessoais (`/tasks/personal`) seguem sem e2e.
- O backend atual não contém módulos de profissionais, setores ou escalas de plantões. Requisitos de desativação de profissionais ou bloqueio por plantões futuros não se aplicam às funcionalidades presentes neste repositório.
- O e2e de despesas cobre as operações principais de lista, criação, edição, exclusão, moradores e criação de subgrupo. Rotas adicionais como pagamento pessoal, lembretes, comprovantes e edição/listagem de subgrupos não aparecem nos testes HTTP e2e listados.
- Os testes de cliente HTTP do frontend cobrem subconjuntos de rotas por feature. Por exemplo, o cliente de despensa testa categorias; itens e movimentações são exercitados no e2e do backend.
- Página, componente, cliente HTTP, controller, serviço e migração são níveis diferentes de teste. Um teste de UI ou de cliente HTTP não comprova por si só o funcionamento da rota no servidor; um e2e com mocks também não comprova persistência real no PostgreSQL.

## Achados da revisão sênior

### Corrigidos nesta revisão

- **Cobertura de backend subestimada:** a configuração não incluía todos os arquivos fonte. Agora `coverage.include` considera `src/**/*.ts`, com exclusão de testes, declarações e código gerado. A medição resultante é 63,16% de linhas, não os 77,9% reportados anteriormente.
- **Build de produção bloqueado por imports ausentes:** `APP_GUARD`, `ThrottlerGuard` e `ThrottlerModule` foram importados em `AppModule`; `pnpm build` agora passa em Node 22.
- **Trocas com cobertura estreita e sem validação HTTP:** foram adicionados casos para regras e estados da troca, validação dos DTOs e e2e das três rotas da feature. Os dois novos arquivos unitários executam 30 casos; o arquivo e2e executa 7.
- **Rate limit de login sem teste de rota:** foi adicionado e2e que confirma 20 respostas aceitas e bloqueio da 21ª requisição a `POST /auth/login`.
- **Asserções permissivas no cabeçalho:** dois `toBeTruthy()` que verificavam SVG foram substituídos por `toBeInTheDocument()`.
- **Avisos/dependências desnecessárias nas configurações Vitest:** os aliases passaram a usar `resolve.tsconfigPaths`; a configuração web agora usa extensão `.mts`. As suítes rodaram sem os avisos antigos de carregamento de configuração.

### Pontos que ainda podem gerar apontamentos

1. **Cobertura global ainda baixa:** o backend mede 63,16% em linhas e 45,50% em branches. `rooms.repository.ts` tem 13,04% de linhas, `tasks.repository.ts` 15,55%; controllers de tasks e DTOs de rooms continuam sem cobertura unitária. Isso é uma medida ampla e honesta de todos os arquivos de produção, mas indica onde novos testes agregariam valor.
2. **Cobertura frontend muito abaixo do limite configurado:** são 47,98% de linhas frente ao limite de 100%; `pnpm test:coverage` termina em código 1 mesmo com os 175 testes passando. O próximo passo é criar testes para os módulos sem cobertura e adotar limites incrementais sustentáveis quando a equipe aprovar uma nova linha de base. Reduzir o limite sem ampliar os testes esconderia a lacuna.
3. **Sem integração PostgreSQL nesta execução:** cinco casos de migração foram ignorados por falta de `TEST_DATABASE_URL`. Os mocks e os e2e não comprovam rollback/transações reais das trocas; seria importante adicionar integração de banco para verificar a troca atômica de responsáveis e o comportamento concorrente.
4. **Bloqueio de conta não é uma regra existente:** há limite de requisições por minuto, mas não bloqueio após tentativas de senha inválidas. Se o requisito pretendido for lockout de conta, é necessário definir e implementar essa regra antes de testar sua existência.
5. **E2E de autenticação usa fixture isolada:** o teste de throttling monta `ThrottlerModule` e `APP_GUARD` no próprio módulo de teste, portanto valida a rota e o guard sob essa configuração; não prova sozinho que o `AppModule` de produção esteja montado corretamente.

As sugestões sobre equipes, setores, escalas/plantões e desativação de profissional não correspondem a módulos deste FullHouse. Também não há planilhas `.xlsx`/`.ods` nem relatório `.txt` no repositório para conferir divergência de contagem ou caminho local de máquina. Essas críticas devem ser associadas ao projeto correto ou acompanhadas dos artefatos antes de serem tratadas como pendências deste relatório.

**Atualizado em:** 15/11/2026

**Escopo:** inventário dos testes existentes em `backend/` e `web/`, seus objetivos, rotas relacionadas e situação da última execução.

## Resumo

| Conjunto                      |                             Inventário | Última situação verificada                       |
| ----------------------------- | -------------------------------------: | ------------------------------------------------ |
| Backend unitário              |                50 arquivos `*.spec.ts` | **375 testes aprovados**                         |
| Frontend unitário/UI          | 64 arquivos `*.test.ts` e `*.test.tsx` | **208 testes aprovados** com Node 22             |
| Backend HTTP/e2e              |            12 arquivos `*.e2e-spec.ts` | **66 testes aprovados**                          |
| Backend integração PostgreSQL |     4 arquivos `*.integration.test.ts` | **9 testes aprovados** em PostgreSQL descartável |

Os números acima vêm das execuções desta revisão. As suítes unitárias do backend e frontend, HTTP/e2e e integração PostgreSQL passaram. A cobertura inclui explicitamente os arquivos de produção; as integrações foram executadas em um contêiner PostgreSQL temporário.

## Como executar

| Diretório  | Comando                                     | O que executa                                                                                              |
| ---------- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `backend/` | `pnpm test`                                 | Testes unitários Vitest em arquivos `*.spec.ts`                                                            |
| `backend/` | `pnpm test:e2e`                             | Testes HTTP/e2e em arquivos `*.e2e-spec.ts`                                                                |

| `web/`     | `pnpm test:coverage`                        | Suíte do frontend com relatório e pisos incrementais de cobertura                                          |

As configurações estão em [backend/vitest.config.ts](../backend/vitest.config.ts), [backend/vitest.config.e2e.ts](../backend/vitest.config.e2e.ts), [backend/vitest.config.integration.ts](../backend/vitest.config.integration.ts) e [web/vitest.config.mts](../web/vitest.config.mts).

## Resultado da última execução

### Backend unitário

Comando: `pnpm test:cov`, dentro de `backend/` (executa a suíte unitária e mede cobertura).

- 50 arquivos passaram.
- 375 testes passaram.
- Duração registrada: aproximadamente 30 segundos com cobertura.
- Execução feita em Node 20.19.2 via `pnpm test:cov`.
- A suíte unitária não exige banco de dados: os testes isolam serviços, repositórios e integrações por mocks.

### Frontend unitário e de interface

Comando: `npm exec --yes --package=node@22 -- pnpm test --run`, dentro de `web/` (Node 22.23.3).

- 64 arquivos passaram, com 208 testes aprovados.
- A execução usou Node 22 temporariamente via `npm exec`; não alterou a versão de Node do sistema.
- A configuração do Vitest foi renomeada para `.mts` e passou a usar resolução de aliases embutida no Vite; a suíte passou sem os avisos de configuração anteriores.

### Medição de cobertura

Cobertura do backend medida com `pnpm test:cov`, usando o provider V8 e inclusão explícita dos arquivos `backend/src/**/*.ts` (exceto arquivos gerados, declarações e testes):

| Métrica    | Cobertura |
| ---------- | --------: |
| Statements |    75,11% |
| Branches   |    58,03% |
| Functions  |    70,01% |
| Lines      |    76,40% |

- O backend usa Vitest, não Jest. Sua configuração declara `coverage.include` para todo `src/**/*.ts`, evitando que módulos não importados pelos testes desapareçam do relatório. O comando correspondente é `pnpm test:cov` dentro de `backend/`.
- Cobertura frontend em `pnpm test:coverage`: statements 62,28%, branches 54,73%, functions 55,87% e lines 64,37%, com os 208 testes aprovados em Node 22. O comando passa com pisos incrementais de 50% para statements e lines, 43% para branches e 44% para functions.
- Esses pisos são uma linha de base de regressão, não uma meta final. Os novos testes exercitam componentes de despesas e a página principal de tarefas; ainda há áreas amplas sem cobertura, como o modal de item da despensa e partes da página de anúncios.

### E2E e integração

O comando `pnpm test:e2e` passou em 12 arquivos e 66 testes em Node 20.19.2. Os testes montam controllers Nest em um servidor HTTP de teste e substituem serviços por mocks; validam rotas, guards, DTOs e ligação controller-serviço, mas em geral não persistência real. Cadastro, logout, recuperação de senha e tarefas pessoais agora têm cobertura HTTP. O teste do limite de login importa o `AppModule` de produção e substitui autenticação e Prisma, verificando a rota na composição real. Os quatro arquivos de integração passaram: os 9 casos foram executados após aplicar as migrações em PostgreSQL 18.1 temporário. O teardown da troca de tarefas foi ajustado para remover pedidos antes dos moradores referenciados. O build de produção também passou com `npm exec --yes --package=node@22 -- pnpm build`. Gere o cliente Prisma com `pnpm db:generate` antes das suítes que importam enums do schema.

O ESLint e o Prettier também passaram nos arquivos alterados.

## Cobertura de rotas: observações

- As rotas de autenticação têm testes unitários do controller/serviço no backend, testes do cliente HTTP/interface no frontend e e2e de cadastro, login, logout, recuperação de senha, throttling e lockout. Os e2e de cadastro/logout/recuperação usam `AuthService` simulado; o lockout exercita `AuthService` real com dependências simuladas, e o throttling importa o `AppModule` de produção.
- O controller limita requisições a 20 por minuto e a aplicação aplica limite global de 120 por minuto ([auth.controller.ts](../backend/src/auth/auth.controller.ts), [app.module.ts](../backend/src/app.module.ts)). O lockout agora bloqueia por 15 minutos após cinco falhas, reinicia a janela ao expirar, zera as falhas após login válido e também limpa o estado no reset de senha. O teste de throttling inicializa o `AppModule` de produção; autenticação e Prisma são substituídos para não depender de banco nem de senha real.
- O e2e de tarefas cobre tarefas residenciais (`/residences/:residenceId/tasks`), pessoais (`/tasks/personal`) e as rotas de troca (`/residences/:residenceId/task-exchange-requests`). Os serviços seguem simulados nesses testes HTTP.
- O backend atual não contém módulos de profissionais, setores ou escalas de plantões. Requisitos de desativação de profissionais ou bloqueio por plantões futuros não se aplicam às funcionalidades presentes neste repositório.
- O e2e de despesas cobre as operações principais de lista, criação, edição, exclusão, moradores e criação de subgrupo. Rotas adicionais como pagamento pessoal, lembretes, comprovantes e edição/listagem de subgrupos não aparecem nos testes HTTP e2e listados.
- Os testes de cliente HTTP do frontend cobrem subconjuntos de rotas por feature. Por exemplo, o cliente de despensa testa categorias; itens e movimentações são exercitados no e2e do backend.
- Página, componente, cliente HTTP, controller, serviço e migração são níveis diferentes de teste. Um teste de UI ou de cliente HTTP não comprova por si só o funcionamento da rota no servidor; um e2e com mocks também não comprova persistência real no PostgreSQL.

## Achados da revisão sênior

### Corrigidos nesta revisão

- **Cobertura de backend subestimada:** `coverage.include` considera todo `src/**/*.ts`, exceto testes, declarações e código gerado. Com a configuração ampla, o backend mede 76,40% de linhas e 58,03% de branches; os novos testes elevam `rooms.repository.ts` e `tasks.repository.ts` a 100% de linhas.
- **Build de produção bloqueado por imports ausentes:** `APP_GUARD`, `ThrottlerGuard` e `ThrottlerModule` foram importados em `AppModule`; `pnpm build` agora passa em Node 22.
- **Trocas com cobertura estreita e sem validação HTTP:** foram adicionados casos para regras e estados da troca, validação dos DTOs e e2e das três rotas da feature. Os dois novos arquivos unitários executam 30 casos; o arquivo e2e executa 7.
- **Rate limit de login sem teste de rota:** foi adicionado e2e que confirma 20 respostas aceitas e bloqueio da 21ª requisição a `POST /auth/login`.
- **Lockout de conta ausente:** foi definida e implementada a política de cinco falhas consecutivas e bloqueio de 15 minutos, com persistência, limpeza no login válido/reset de senha e reinício após expiração. Os testes cobrem serviço, repositório, rota e migração.
- **E2E isolado da composição de produção:** o teste de throttling agora importa o `AppModule` real e verifica o limite na rota; `app.module.spec.ts` também verifica a presença do guard/configuração global.
- **Cobertura web bloqueava `test:coverage`:** foram acrescentados testes para clientes de tarefas, pets e residências, utilitários, componentes de despesas e a página principal de tarefas. A cobertura de linhas chegou a 64,37%; `pnpm test:coverage` passa com pisos incrementais de 50% statements, 43% branches, 44% functions e 50% lines.
- **Áreas backend apontadas sem cobertura:** foram adicionados testes para repositórios de quartos e tarefas, DTOs de quartos e tarefas e controllers de tarefas residenciais, pessoais e trocas.
- **Asserções permissivas no cabeçalho:** dois `toBeTruthy()` que verificavam SVG foram substituídos por `toBeInTheDocument()`.
- **Avisos/dependências desnecessárias nas configurações Vitest:** os aliases passaram a usar `resolve.tsconfigPaths`; a configuração web agora usa extensão `.mts`. As suítes rodaram sem os avisos antigos de carregamento de configuração.

### Limitações remanescentes

1. **Cobertura global ainda pode crescer:** a medição ampla do backend está em 76,40% de linhas/58,03% de branches e a do frontend em 64,37%/54,73%. O piso web é uma proteção incremental e não significa que todas as áreas estejam cobertas. Há lacunas em outros módulos, como itens da despensa, anúncios e os componentes isolados de calendário/lista de tarefas.
2. **Escopo de rotas:** cadastro/logout/recuperação e tarefas pessoais agora têm cobertura HTTP e2e. Esses testes usam serviços simulados; para a maioria dos módulos, ainda faltam fluxos e2e que exercitem persistência de ponta a ponta. As suítes PostgreSQL comprovam as migrações e os fluxos de troca cobertos, não todas as rotas da aplicação.

As sugestões sobre equipes, setores, escalas/plantões e desativação de profissional não correspondem a módulos deste FullHouse. Também não há planilhas `.xlsx`/`.ods` nem relatório `.txt` no repositório para conferir divergência de contagem ou caminho local de máquina. Essas críticas devem ser associadas ao projeto correto ou acompanhadas dos artefatos antes de serem tratadas como pendências deste relatório.
